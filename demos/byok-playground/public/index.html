Your key, your endpoint, a Worker that refuses to store either

Contact

What this shows A Worker can proxy a visitor’s OpenAI-compatible key without becoming an open proxy: the key lives in this browser, SSRF is blocked, redirects are refused, and Workers AI comparison is Turnstile-gated with a daily budget.

What you can try

  • Paste a key, an https base URL, and a model id, then stream a chat.
  • List models from GET /models.
  • Send the same prompt to your model and to Workers AI, and read latency, time to first token, and tokens.
  • Probe streaming, tools, JSON schema, and vision. Each check is pass, fail, or unsupported, with the raw error.

What you could build

  • A product that accepts a customer’s OpenAI-compatible key without writing it to disk.
  • A migration bench that compares a provider against Workers AI on the same prompt.
  • An eval harness that records which capabilities an endpoint actually implements.

Your endpoint

The key is never written on the Worker. It is sent per request in a header, then dropped. Errors and logs strip it. Session storage is the default; Remember keeps it in this browser only.

Streaming chat

SSE passthrough to /chat/completions. Output is rendered as text, never HTML.
